# 漏えい事案の更新手順（毎時ルーティン用）

このリポジトリは GitHub Pages（https://skikkh.github.io/jp-security-announcement/ ）で公開している市民向けの自衛ガイドです。
毎時のルーティンは、この手順に従って「主な漏えい事案」（`src/data/breaches.json`）を更新し、`main` に直接 push します。
リポジトリのオーナーは、新規事案の追加と続報の反映について `main` への直接 push を許可しています。

## 1. 準備

```sh
git fetch origin main
git checkout main
git pull --ff-only origin main
git log -1 --format='%cI %s' origin/main   # 前回の更新時刻

# git config の user.name / user.email は変えない（コミッターは Claude のまま。署名が付く）
git config --unset user.name 2>/dev/null; git config --unset user.email 2>/dev/null
```

**コミットの作成者（author）はリポジトリのオーナーにする（必須）。** 次のように `--author` を付けてコミットする。
コミッターは環境の設定（Claude）のままにする。そうすると署名が付き、GitHub で「Verified」と表示される。

```sh
git commit --author="Ikki Shoka <16469483+skikkh@users.noreply.github.com>" -m "..."
```

コミットメッセージの末尾には、セッションの案内どおり Claude を共同作成者（Co-Authored-By）として付けてよい。

`src/pages/about.html` の「更新履歴」と `src/data/breaches.json` を読み、すでに載っている事案を把握します。

## 2. 調べる範囲

- **期間**：前回の更新以降に公表されたもの。最低でも直近48時間を見る。
- **対象**：日本国内の企業・団体・行政が公表した、利用者・会員・顧客の個人情報の漏えい（可能性・おそれを含む）。
  従業員だけの事案は、対象が1万人以上なら追加してよい。
- **続報**：既存事案の件数の修正、専用窓口の新設・変更、受付時間の変更、対象項目の追加・訂正も確認して反映する。
- **候補探しに使う情報源**：JPCERT/CC、個人情報保護委員会、内閣官房国家サイバー統括室、金融庁、Security NEXT、ScanNetSecurity、ITmedia NEWS、INTERNET Watch、piyolog、NHK、共同通信、https://ai.itokoba.com/security-tier/ 。
  これらは**候補を見つけるためだけ**に使う。電話番号や事実の出典にはしない。

## 3. 事実確認のルール（最重要）

1. 追加・更新する事実は、**その会社の公式ドメインの発表**（または TDnet、eir-parts などの公式IR PDF）で確かめたものに限る。
2. **問い合わせ窓口**（電話・メール・フォーム）は、公式発表に「本件の窓口」として書かれているものだけを、そのまま書き写す。
   IR、報道機関向け、加盟店・取引先向けの窓口は載せない。まとめサイトや報道からの転記は禁止。
3. 公式発表を開けないときは、`contact` を入れない（サイト上は「確認できていません」と表示される）。
   その場合は `src` を `"報道"` にし、信頼できる報道のURLを `url` に入れる。
4. 件数は公式発表の表記に従う。「最大」「延べ」「可能性」「人数ではない」などの注記を落とさない。報道と公式で数字が違うときは、どちらの数字かを明記する。
5. **不正アクセスの確認と個人情報の漏えい確認を混同しない。**公式発表が「閲覧または取得された可能性がある」「漏えいのおそれ」としている場合、`status` は `"可能性"` にする。漏えいそのものを確認したと公式に発表された場合だけ `"確認"` にする。東京メトロのように不正アクセスは確認済みでも取得は可能性の段階という事案がある。
6. 新規・更新する各行について、公開前に公式発表の該当箇所と `status`、`count`、`items`、`contact` を一つずつ照合する。`tools/build.py` は形式の検査であり、事実の正しさや窓口が本件専用かどうかは判定できない。
7. 確かめられないものは追加しない。誤った情報を出すより、載せないほうがよい。

## 4. データ形式（`src/data/breaches.json` の1件）

```json
{
  "date": "2026-10-09",
  "date_label": "2026年10月9日",
  "org": "会社名",
  "service": "サービス名（なければ空文字）",
  "kana": "検索用のよみがな 英字名",
  "count": "最大 約643万件（会員番号の件数）",
  "status": "確認",
  "items": ["氏名", "住所", "電話番号"],
  "note": "補足（なければ空文字）",
  "url": "https://（出典。公式発表があればそれ）",
  "src": "公式",
  "official": "https://（url が報道のとき、公式発表のURL。任意）",
  "contact": {
    "name": "窓口の名前",
    "tels": ["0120-000-000"],
    "hours": "受付時間（公式の表記に沿って）",
    "emails": ["example@example.co.jp"],
    "forms": [{"label": "専用お問い合わせフォーム", "url": "https://..."}],
    "note": "補足"
  }
}
```

- `status`：`"確認"`（漏えい確認）、`"可能性"`（可能性・おそれ）、`"調査中"` のいずれか
- `src`：`"公式"` か `"報道"`
- `date`：公表日。続報で更新したときは最初の公表日のままにし、`date_label` を「2026年9月29日（10月9日に第3報）」のようにする
- `items` に使えるタグ（これ以外はビルドで止まる）：
  氏名、住所、電話番号、メールアドレス、生年月日、性別、会員ID、パスワード、本人確認書類の画像、免許証番号、パスポート情報、本人確認書類の番号、カード情報の一部、口座情報、購入・配送・利用履歴、家族情報、勤務先・所属、その他（詳細は出典）
- `contact` の中で使うキーは上の6つだけ。不要なキーは省く。窓口を載せるときは、公式発表のURL（`src` が公式の `url`、または `official`）が必須

## 5. 手順

1. 候補を集め、既存の事案（`org` と `service`）と照らして重複を除く
2. 候補ごとに公式発表を開いて確かめ、上の形式で1件を作る
3. `src/data/breaches.json` に追加・更新する（表示は日付順に自動で並ぶ）
4. `tools/build.py` の `UPDATED`（例：`2026年10月9日`）と `UPDATED_ISO` を日本時間の今日にする
5. `src/pages/about.html` の「更新履歴」の先頭に1行足す
   例：`<li>2026年10月10日：漏えい事案に〇〇を追加。△△の窓口を更新</li>`
6. `python3 tools/build.py` を実行する。検査に失敗したら直す
7. 追加・変更したURLを `curl -sSL -o /dev/null -w '%{http_code}'` で確かめる。403 はボット対策のことがあるので、ブラウザ相当のUAで再確認する
8. コミットして `git push origin HEAD:main`
   拒否されたら `git pull --rebase origin main`。`docs/` が衝突したら `python3 tools/build.py` で作り直して解決し、再度 push（最大3回）
9. 変更がなければ、何もコミットしない

## 6. してはいけないこと

- 既存の事案を消さない（誤りの訂正はよい。理由をコミットメッセージに書く）
- 各ページの説明文やデザインを変えない。変えてよいのは `src/data/breaches.json`、更新日、更新履歴だけ
- 外部スクリプト、アクセス解析、広告を加えない
- 攻撃者を断定したり、個人を特定したりする記述をしない
- プルリクエストは作らない

## 7. 最後の報告

実行の最後に、追加・更新した事案と確認した公式発表のURLを短くまとめる。何もなければ「新規なし」とだけ書く。
